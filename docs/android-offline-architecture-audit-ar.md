# تدقيق تحويل ترتيل إلى Android Offline‑First

## حالة التدقيق

هذا التقرير يوثق خط الأساس قبل أي تحويل معماري. المشروع الحالي هو **تطبيق ويب React/Vite مع خادم Express وtRPC وقاعدة MySQL/TiDB عبر Drizzle**. يوجد مجلد `android-wrapper/`، لكنه غلاف Capacitor يعتمد صراحةً على `server.url` والرابط المنشور، ولذلك لا يحقق متطلبات تطبيق Android مستقل أو Offline‑First.

> لا يُعد APK Debug الحالي دليلاً على وجود تطبيق Android أصلي. كما لا يجوز اعتبار إزالة شاشة التحميل أو إضافة cache بديلاً عن قاعدة محلية ومزامنة موثوقة.

## النتائج المؤكدة

| المجال | الوضع الحالي | الأثر على التحويل |
|---|---|---|
| الواجهة | React 19 وReact DOM وWouter وTailwind/shadcn | لا يمكن تشغيل هذه الواجهة كواجهة Android أصلية من دون إعادة بناء طبقة العرض أو اختيار خطة انتقال مرحلية صريحة. |
| الخادم | Express وtRPC 11 وOAuth وDrizzle | يمكن إعادة استخدام عقود الخادم، لكن لا توجد طبقة Sync API مخصصة أو عقد version/conflict مكتمل. |
| قاعدة البيانات | MySQL/TiDB على الخادم، وschema يضم 29 جدولاً فعلياً تقريباً | الهاتف يحتاج SQLite محلية وترحيلات مستقلة؛ لا يجوز تشغيل MySQL داخل الهاتف. |
| المصادقة | جلسة Manus OAuth وcookie على الخادم | يلزم token/session قابل للتخزين المحمي، ونسخة صلاحيات ونطاقات محلية للعمل بعد أول دخول Online. |
| الغلاف الحالي | Capacitor مع `server.url = https://tarteel-qura-8kmxg5hu.manus.space` | غير مقبول كحل نهائي؛ يعتمد على الإنترنت والموقع المنشور. |
| المزامنة | لا توجد جداول أو خدمة Outbox/Sync/Conflict ظاهرة في الكود الحالي | يجب تصميمها وإضافتها بصورة backward-compatible قبل ادعاء دعم Offline للكتابة. |
| المصحف | منطق قارئ وفهارس وبيانات تعريف في `client/src` و`shared` | منطق التنقل قابل لإعادة الاستخدام، لكن أصول الصفحات نفسها ليست bundled في المشروع الحالي ويجب توفير استراتيجية Offline موثقة. |
| التقارير | PDF/Excel/Text على الخادم وبعض منطق التقرير في الويب | يلزم فصل نموذج التقرير عن مولد الخادم أو توفير مولد محلي مناسب لـ Android. |
| الاختبارات | TypeScript ناجح و156 اختبار Vitest ناجحاً في خط الأساس | هذه اختبارات خادم/ويب وليست اختبارات Android أو SQLite أو انقطاع الشبكة. |
| البناء | workflow الحالي يبني `assembleDebug` لغلاف Capacitor | لا ينتج Release APK أو AAB أصلياً ولا يثبت Offline. |

## الكيانات الفعلية التي يجب مراعاتها محلياً

يستخرج المخطط الحالي الكيانات التالية: `users`, `organizations`, `centers`, `reporting_goals`, `reporting_preferences`, `center_memberships`, `permission_grants`, `user_scopes`, `access_codes`, `access_code_attempts`, `parent_student_links`, `branches`, `academic_seasons`, `circles`, `circle_periods`, `teachers`, `teacher_invites`, `students`, `sessions`, `attendance`, `memorization`, `revision`, `evaluation`, `notifications`, `quran_bookmarks`, `quran_verse_preferences`, و`audit_log`.

هذه القائمة ليست كافية وحدها لإنشاء SQLite؛ يجب تحويل أنواع MySQL إلى أنواع SQLite، تعريف المفاتيح والفهارس وسياسة الحذف الناعم، ثم إضافة جداول تشغيل محلية مثل `sync_outbox`, `sync_conflicts`, `sync_metadata`, و`local_session` من دون تعديل البيانات الإنتاجية تدميرياً.

## قرار معماري مرحلي

التحويل المطلوب لا يمكن إنجازه بأمان في تعديل واحد صغير. المسار الصحيح هو إنشاء تطبيق Android مستقل في مجلد منفصل، ثم بناء طبقة مشتركة للعقود والأنواع حيثما أمكن، مع إبقاء Web App يعمل على Repository الخادم الحالي أثناء تطوير تطبيق الهاتف. بعد تثبيت عقد المزامنة واختبارها، تُنقل الوحدات إلى التدفق التالي:

```text
Android UI
  ↓
Local Repository
  ↓
SQLite + local authorization + outbox
  ↓
Sync Engine
  ↓
tRPC/Sync API متوافق مع الخادم
  ↓
MySQL/TiDB عبر الخادم
```

لا يجوز استخدام `localStorage` كقاعدة رئيسية، ولا تخزين كلمات المرور، ولا وضع أسرار الخادم داخل APK. كما لا يجوز حذف `server.url` من الغلاف الحالي ثم تسميته تطبيقاً Offline؛ يجب أولاً توفير production bundle محلي أو واجهة Android أصلية حقيقية مع قاعدة محلية.

## ما يمكن تنفيذه الآن وما يحتاج مرحلة لاحقة

| الفئة | قرار أولي |
|---|---|
| القراءة المحلية للمصحف والبيانات الثابتة | قابلة للتنفيذ بعد توفير الأصول أو مصدر مرخص bundled داخل التطبيق. |
| القراءة المحلية للبيانات التي تم تنزيلها | قابلة للتنفيذ عبر SQLite وRepository. |
| إنشاء وتعديل الحضور والحفظ والمراجعة Offline | لا تُعلن قبل وجود Outbox ومعرّفات عملية idempotent وعقد مزامنة وتعارض. |
| المصادقة Offline | ممكنة بعد أول دخول Online عبر Secure Storage ولقطة صلاحيات منتهية الصلاحية وفق سياسة واضحة. |
| التصدير المحلي | ممكن بعد نقل نموذج التقرير ومولد مناسب للهاتف؛ لا يعتمد على نجاح API. |
| الإشعارات الخادمة | Online-enhanced؛ يمكن إضافة إشعارات محلية مستقلة للعمليات المحلية. |
| Release APK/AAB | يتطلب مشروع Android قابل البناء، اختبارات فعلية على جهاز/محاكي، وأسرار توقيع يضيفها المالك إلى GitHub Secrets. |

## الخلاصة

النسخة الحالية سليمة كويب، لكنها **ليست بعد تطبيق Android Offline‑First**. الخطوة التالية الآمنة هي تنفيذ التصميم والهيكل الأولي للتطبيق الأصلي وقاعدة SQLite التجريبية مع اختبارات Repository، وليس تغيير الغلاف الحالي أو إصدار APK يدّعي الاستقلال. يبقى أي إعلان عن Release Production مشروطاً باجتياز اختبارات انقطاع الشبكة، حفظ البيانات بعد إغلاق التطبيق، المزامنة، الترقية، والتوقيع.
